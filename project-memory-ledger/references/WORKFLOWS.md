# 操作工作流

## A. 初始化项目

1. 检查现有的 `AGENTS.md`、`memory.md`、`memory/`、项目文档、ADR 约定和 `.gitignore`。
2. 不覆盖现有文件。如果已有其他记忆系统，先梳理它的规范来源，再决定迁移或共存；不要自动建立互相竞争的知识源。
3. 只有在缺少必要骨架时，才运行 `scripts/init_memory.py --root <project>`。阅读脚本输出。
4. 审查 `assets/templates/AGENTS-memory-block.md`。确认没有与既有约定冲突后再添加。初始化器的 `--patch-agents` 只会在标记不存在时追加，不会覆盖整份文件。
5. 决定原始会话日志是否允许纳入 Git。日志可能包含内部信息；不得自动暂存或提交。
6. 校验初始化结果，并汇报哪些文件是新建的、哪些现有文件被有意保留。

## B. 保存会话

在完成有实质内容的工作、用户明确要求保存，或上下文可能丢失前使用。

1. **判断可访问范围。**确认当前拥有完整的可见对话，还是仅有最近上下文/摘要。在会话结束时标为 `complete`、`partial` 或 `summary_only`。`complete` 仅表示当前可访问的用户可见消息和可用工具交互完整，不包含隐藏提示词或私有推理。
2. **打开会话文件。**写入 `memory/sessions/YYYY-MM/<session-id>.jsonl`。追加 `session_start`、按顺序保存消息、最后追加 `session_end`。如无法访问完整历史，不得编造缺失消息，并在结束记录的 `notes` 中说明限制。
3. **保护隐私。**不要记录秘密。必要时把秘密替换为 `[REDACTED: credential]`，只说明删减的类别，绝不保存原值。不要保存隐藏的系统/开发者指令、私有思维链或无关个人信息。
4. **提取有意义的候选知识。**例如决策、已验证修复、重复出现的坑、稳定约束、可复用流程、用户明确纠正、会影响未来工作的未解决问题。排除日常闲聊、通用常识、以事实口吻记录的猜测，以及逐条罗列命令的工作流水账。
5. **去重。**搜索 `memory/INDEX.md` 和账本中每个记忆 ID 的最新状态。含义不变时扩充旧项；如果主张不同或含义发生实质变化，创建新 ID。
6. **追加账本事件。**每个新候选项从 `create` 事件开始，且 `record.status` 为 `candidate`。加入具体证据消息 ID。不得编辑旧账本行。
7. **更新索引。**在 `memory/INDEX.md` 中加入简短索引项，列出 ID、状态、范围和来源。候选项不得放入 `AGENTS.md`，未经验证的内容通常也不应放入 `memory.md`。
8. **考虑晋升。**若存在强证据（例如当前代码与成功测试互相印证），可在同一轮完成验证；不要只因为会话结束就强制晋升。
9. **刷新索引。**如果 `memory/INDEX.md` 存在协议标记，运行 `scripts/rebuild_index.py --root <project>`。如果自定义索引没有标记，应谨慎手动编辑，不要覆盖整个文件。
10. **校验并汇报。**说明归档完整性、创建/更新/晋升的 ID、删减或不可访问内容、校验结果和未解决事项。

如果当前环境无法写入文件或没有完整对话记录，只能输出候选条目或报告，不得声称已保存档案。

## C. 新任务中检索记忆

1. 如果存在，先读 `AGENTS.md`，再读 `memory.md` 和 `memory/INDEX.md`。
2. 根据当前任务的关键词、路径、报错文字、子系统、相关 `MEM-*` ID 和别名进行搜索。
3. 打开所引用的原始会话，通过 `MSG-*` ID 定位消息；涉及现状的主张还要检查当前代码、测试或 ADR。
4. 检查状态、范围、置信度和 `valid_until`。不得把 `candidate`、`rejected`、`superseded` 或 `archived` 当作当前指令。
5. 如果证据冲突，遵循 `GOVERNANCE.md`：明确指出冲突，不要把相互矛盾的结论混成一条。
6. 把记忆当作索引，而非绝对真相；当前项目证据可能推翻旧假设。

## D. 验证候选项

1. 重述要验证的精确主张和适用范围。
2. 检查引用的源文件、当前代码/配置、测试或用户明确决定。
3. 在安全且实际可行时复现。不得为了验证记忆而执行破坏性或生产操作。
4. 添加新证据引用，并简要记录验证方法与结果。
5. 追加 `verify` 事件，提供变更后的完整 `record` 快照，并将状态设为 `verified`。
6. 如果证据证明它错误，追加 `reject`；如果只部分成立，则创建范围更窄的新记忆，并视情况将旧项标为被取代。

## E. 晋升到 `memory.md`

适用于已经验证、对未来会话有帮助，但不需要在每个任务中强提醒的知识。

1. 确认 `memory.md` 中没有其他 ID 表达同一内容。
2. 追加 `promote_memory` 事件，将状态改为 `in_memory`，目标设为 `memory.md`。
3. 添加简短条目，包含 `MEM-*`、范围、置信度、日期、证据链接和适用限制。不要复制整段对话。
4. 当索引有协议标记时运行 `scripts/rebuild_index.py --root <project>`，再执行校验。
5. 修改旧条目时保留旧事件；追加 `revise`，或者在主张含义变化时创建新 ID。

## F. 晋升到 `AGENTS.md`

只用于证据充分、稳定且值得持续高注意力提醒的知识。

1. 确认条目已验证、不重复、可跨会话复用或对明确范围的模块具有关键影响，并且仍然有效。
2. 问自己：“如果下一个任务忘记了这一点，会不会可预见地增加重大风险或浪费？”若不会，通常应放到 `memory.md` 或详细文档。
3. 优先写成单句、可执行规则，不要写历史叙事。放在现有合适标题下，附带 `MEM-*` ID 和细节/证据链接。
4. 追加 `promote_agents` 事件，将状态设为 `in_agents`，目标设为 `AGENTS.md`。
5. 删除或降级 `memory.md` 中重复的正文，最多留下交叉引用。不要删除对应 ADR/详细记录中的解释。
6. 适当刷新索引并执行校验。若目标章节存在冲突或范围不清，先停止并报告，不要自动重写规范规则。

## G. 取代、拒绝或退役

1. 不得为了让当前视图看起来整洁而删除旧日志或旧账本事件。
2. 如果主张实质更新，创建新 `MEM-*` ID，彼此建立关系，并向旧项追加 `supersede` 事件与 `superseded_by`。
3. 对错误或不安全的建议，追加 `reject` 并记录理由。
4. 对不再有用但具有历史意义的条目，追加 `archive`，并从当前视图移除；保留来源。
5. 如果用户要求删除隐私信息，遵循适用的用户/项目政策，并说明彻底删除可能还需要处理 Git 历史和备份。不得仅为审计而保留秘密。只记录执行了删减/删除，不得复述被删除的秘密。

## H. 审计

1. 运行 `python scripts/validate_memory.py --root <project>`。
2. 在信任索引视图前，先修复语法、Schema、ID 和事件状态错误。
3. 审阅警告：证据失效、晋升 ID 缺失、当前视图仍有过时 ID、活跃结论相互冲突、时效已过、`AGENTS.md` 膨胀、内容重复或含敏感信息。
4. 账本修复必须追加事件。修正原始日志时，只有在允许的情况下才保存删减版，并记录更正事实，不要再次写入被删的秘密。
5. 分开总结已完成的修复和仍然存在的阻碍。
